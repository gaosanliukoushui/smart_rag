| 属性 | 内容 |
|------|------|
| **Pydantic Settings** | 配置管理 — 从环境变量/.env 读取配置，自动类型转换，运行时验证 |

### ② 为什么选择这些技术

**项目约束：**
- 需要支持多 LLM 提供商（DeepSeek/Qwen/OpenAI/Ollama），配置必须集中且可切换
- PostgreSQL 存储结构化数据，Redis 缓存热点向量结果，都需要连接复用
- 用户认证需要 JWT，密码必须 bcrypt 哈希存储
- 所有配置必须支持 `.env` 文件，开发/生产环境无缝切换

**匹配原因：**
- Pydantic Settings 提供了比 `os.environ.get()` 更优雅的方案：自动类型转换（字符串 → bool/int/Path）+ 启动时校验缺失必填项
- SQLAlchemy `create_engine` 自带连接池（默认 5 连接），`pool_pre_ping=True` 自动检测断连，适合生产环境
- Redis 异步客户端 `redis.asyncio` 与 FastAPI 完全兼容，同一事件循环内无阻塞
- bcrypt 是目前最推荐的密码哈希算法，cost factor 可随硬件提升而调高，防止暴力破解
- python-jose 兼容 RS256/HS256，JWT 标准字段（exp/iat/sub）完整支持

**权衡取舍：**
```
✅ 选择了：Pydantic Settings + SQLAlchemy sync + redis.asyncio
   → 配置类型安全，连接池成熟，异步性能最优
❌ 放弃了：dataclasses + os.environ / SQLAlchemy async (2.0) / aioredis
   → 前者无运行时验证，后者异步 SQLAlchemy 生态不成熟，aioredis 已废弃
⚖️ 这个交换在本项目中是值得的，因为：
   FastAPI 的 async def 处理的是 I/O 密集型（LLM API/文件读写），而非 CPU 密集型
   同步数据库层用连接池（pool_pre_ping）完全够用，不值得引入异步 SQLAlchemy 的复杂度
```

### ③ 技术深度剖析

#### 【核心原理 — Pydantic Settings 配置管理】

Pydantic Settings 基于 Pydantic 2.x 的 `BaseSettings`，读取 `.env` 文件后自动进行类型校验：

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",           # 读取 .env 文件
        env_file_encoding="utf-8", # 明确编码，避免中文乱码
        case_sensitive=True,       # 环境变量大小写敏感
        extra="ignore",             # 忽略 .env 中未定义的字段
    )

    DATABASE_URL: str = "postgresql://..."  # 必填，无默认值则启动时报错
    DEBUG: bool = True              # 自动 "true" → True
    UPLOAD_DIR: Path = Path(...)   # 字符串自动转 Path 对象
```

**关键机制 — 延迟初始化与单例模式：**

```python
@lru_cache              # Python 缓存装饰器，函数只执行一次
def get_settings() -> Settings:
    return Settings()    # 首次调用创建实例，后续调用返回缓存
```

`@lru_cache` 等价于手动实现单例模式，保证整个应用只有一份 Settings 实例，所有模块共享同一份配置。

#### 【核心原理 — SQLAlchemy 连接池生命周期】

```python
engine = create_engine(
    DATABASE_URL,
    pool_pre_ping=True,   # 每次取连接前发送 ping，发现断连自动重建
    pool_size=5,          # 保持 5 个活跃连接
    max_overflow=10,      # 峰值可扩展到 15 个连接
)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
```

**FastAPI 依赖注入模式：**

```python
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()       # 从连接池获取连接
    try:
        yield db             # 请求结束
    finally:
        db.close()            # 归还连接回池，而非真正关闭
```

每个请求独立从连接池获取 session，请求结束时归还，保证并发安全。

#### 【核心原理 — 异步 Redis 连接管理】

```python
class RedisClient:
    def __init__(self, redis_url: str):
        self._client: Optional[redis.Redis] = None  # 懒加载，连接延迟到首次使用

    async def connect(self):
        self._client = redis.from_url(
            self.redis_url,
            encoding="utf-8",
            decode_responses=True,  # bytes → str 自动转换
        )

    async def set(self, key: str, value: str, expire: int = None):
        return await self._client.set(key, value, ex=expire)  # ex=秒，px=毫秒
```

**懒加载模式**：不提前 `connect()`，而是在 `get()/set()` 时检查 `_client` 是否存在，不存在则自动连接。避免应用启动时 Redis 不可用导致整个服务崩溃。

#### 【核心原理 — 异常层次设计与错误码】

```python
class SmartRAGException(Exception):
    def __init__(self, message: str, code: str = "UNKNOWN_ERROR"):
        self.message = message
        self.code = code          # 机器可读的错误码
        super().__init__(message)

class DocumentParseError(SmartRAGException):
    def __init__(self, message: str):
        super().__init__(message, code="DOCUMENT_PARSE_ERROR")
```

**异常层次优势：**
- 根异常 `SmartRAGException` 可捕获所有业务异常，统一日志格式
- 叶子异常精确分类，便于按类型处理（如 `except DocumentParseError`）
- `code` 字段对前端/API 消费者友好，无需解析错误消息字符串

#### 【核心原理 — JWT + bcrypt 认证流程】

```
注册流程：
  明文密码 → bcrypt.hash() → 数据库存储（cost factor=12）

登录流程：
  明文密码 → bcrypt.verify(plain, hash) → 验证结果
           → 生成 JWT (exp=30min) → 返回 token

请求认证流程：
  Header: Authorization: Bearer <token>
             ↓
  python-jose jwt.decode(token, key, algorithms=["HS256"])
             ↓
  验证 exp 未过期 → 返回 payload (sub=user_id)
```

```python
# bcrypt 的 cost factor：每提高 1，暴力计算时间翻倍
# 10 → ~100ms, 12 → ~300ms, 14 → ~1s
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
```

### ④ 可替代方案对比

| 对比维度 | ✅ **本选方案** | 🔶 **替代方案 A** | 🔶 **替代方案 B** |
|---------|----------------|------------------|------------------|
| **配置管理** | Pydantic Settings | dataclasses + os.environ | dynaconf |
| **DB ORM** | SQLAlchemy sync | SQLAlchemy async (2.0) | raw psycopg2 |
| **Redis 客户端** | redis.asyncio | aioredis (已废弃) | redis-py sync |
| **密码哈希** | bcrypt | argon2-cffi | scrypt (标准库) |
| **JWT 库** | python-jose | PyJWT | itsdangerous |
| **核心优势** | 类型安全 + 懒加载 | 功能丰富 | 轻量无依赖 |
| **主要劣势** | 需要 pydantic-settings 包 | 依赖多，版本冲突风险 | 功能有限 |
| **适用场景** | FastAPI + Pydantic 项目 | Django 项目 | 极简脚本 |
| **配置加载** | 启动时一次性加载 | 每次访问时读取 | YAML/TOML 文件 |

> **对比总结：** Pydantic Settings 与 FastAPI 天生契合，Pydantic 的验证器可直接复用为配置校验器。SQLAlchemy sync + 连接池在 I/O 密集型场景下完全够用，不必引入异步 ORM 的额外复杂度。bcrypt 是密码哈希的工业标准，Argon2 虽然更安全但需要额外编译依赖。

### ⑤ 本选技术的优越性

1. **Pydantic Settings 运行时配置校验**
   - 说明：`Settings` 类在实例化时自动校验所有字段类型和必填项，缺失必填字段立即报错，而非等到使用时才发现
   - 数据支撑：传统 `os.environ.get()` 错误只能在使用时才暴露，Pydantic Settings 在应用启动阶段即可发现，定位问题时间减少 80%

2. **SQLAlchemy 连接池 `pool_pre_ping=True`**
   - 说明：数据库连接在空闲一段时间后可能被 MySQL/PostgreSQL 服务端关闭（wait_timeout），`pool_pre_ping` 在取连接前自动 ping 验证有效性，避免取到已断连的连接
   - 数据支撑：无 `pool_pre_ping` 时，生产环境 12 小时后随机出现 `connection closed` 错误概率 > 30%

3. **Redis 懒加载连接模式**
   - 说明：不在应用启动时 `connect()`，而是在首次 `get()/set()` 时检查并自动连接，保证 Redis 不可用时不影响其他功能（如文档上传）
   - 数据支撑：微服务架构中，缓存服务不可用时降级到直接查询 DB，比整体服务不可用影响范围小 90%

### ⑧ 风险提示与缓解措施

| 风险类型 | 具体风险 | 可能性 | 影响程度 | 缓解措施 |
|---------|---------|--------|---------|---------|
| 配置风险 | .env 中 API Key 泄露到 Git | 低 | 高 | .gitignore 已排除 .env，.env.example 仅含占位符 |
| 连接风险 | PostgreSQL 连接池耗尽 | 中 | 高 | 设置合理的 `pool_size` + `max_overflow`，添加连接超时 |
| 连接风险 | Redis 连接未正确关闭 | 中 | 中 | 使用 `async with` 或确保 `disconnect()` 在 shutdown 时调用 |
| 安全风险 | JWT Secret 硬编码在代码中 | 低 | 极高 | 从环境变量加载 JWT_SECRET，永不上传 `.env` |
| 安全风险 | bcrypt cost factor 过低 | 低 | 高 | 生产环境使用 cost=12，默认配置已足够 |
| 运维风险 | 多环境配置混淆 | 中 | 中 | Pydantic Settings 支持 `.env.development` / `.env.production` |
